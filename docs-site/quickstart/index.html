Technical implementation requirements for the Farcaster client prize. A genuine submission must work without borrowed read API keys, explain validator writes, and make account key onboarding safe.

Acceptance target · not yet certified

What the prize actually asks

In his October 17 cast, Balaji offered $2,048 for better developer onboarding: (0) provision compute, (1) set up a Snapchain read node, and (2) create a client that reads from it. He also asks for validator-based writes, importing an existing account's seed phrase, authorizing an app key on Optimism, basic social actions and client-specific inclusion/exclusion filtering.

Do not submit a mock three-command demo as a completed tutorial.

These are three target stages. There is no audited, verified Genycaster command sequence today that fulfills all three, so this page intentionally does not fabricate one.

Three-stage execution blueprint

0 Provision compute

Dedicated Linux VPS or machine; upstream baseline: 4 vCPU, 16 GB RAM, 1.5 TB free SSD, public IP and ports 3381–3383 TCP/UDP. Scripted provisioning is a future acceptance task.

1 Bootstrap and synchronize Snapchain

Follow official upstream instructions. Review the installation script before executing it, especially on a server with other workloads.

Upstream bootstrap — review first
curl -fsSL https://raw.githubusercontent.com/farcasterxyz/snapchain/refs/heads/main/scripts/snapchain-bootstrap.sh -o snapchain-bootstrap.sh\nless snapchain-bootstrap.sh\nbash snapchain-bootstrap.sh
Local node status
curl --fail-with-body http://127.0.0.1:3381/v1/info

Monitor maxHeight and blockDelay; merely receiving HTTP 200 does not prove the node is synchronized or has every user profile.

2 Connect a client; publish via a separate route

In Genycaster's beta settings, choose Node management → Add read node → Snapchain node; set a reachable URL and test it. A browser may require HTTPS and approved CORS. No switch magically turns a read-only node into a validator; writers and app keys are configured separately.

Read-only API smoke examples
curl --fail-with-body 'http://127.0.0.1:3381/v1/castsByFid?fid=3&pageSize=1&reverse=true'\ncurl --fail-with-body 'http://127.0.0.1:3381/v1/userDataByFid?fid=3&pageSize=100'

Account setup and write security

  1. Existing account: Keep the custody seed phrase entirely on a trusted device; never paste it into a website, documentation page or node provider.
  2. Authorize client key: Sign the proper Farcaster signer authorization on OP Mainnet with custody, checking the current contract and chain configuration using the official protocol documentation.
  3. Publish: Sign canonical Farcaster protocol messages locally with the authorized app key; submit to a write-capable validator. A reader can remain read-only.
  4. Verify: Reconcile by canonical message hash against a protocol reader. Do not silently reassign in-flight writes when switching providers.

This is the required security design, not a claim that Genycaster's full import UI is already delivered.

Evidence expected for a prize submission

Include a public repository with pinned versions, verified three-command install, a zero-managed-key network trace, node sync evidence, a cast / reaction / follow confirmation, an app-key authorization transaction hash, and a reproducible client-origin filtering test. Current status and gaps →
